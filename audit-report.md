## Chat Server — Issues

### 🔴 CRITICAL

**GeminiService.java line 93 — API key exposed in URL query parameter**

```java
String url = API_BASE + model + ":generateContent?key=" + apiKey;
```

The API key is appended to the URL. Every HTTP client library, proxy, server log, firewall, and CDN logs the full URL — including the key. Google's own recommendation is to pass it in an `Authorization: Bearer` header.

**Fix:** Change to header-based auth:
```java
String url = API_BASE + model + ":generateContent";
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create(url))
        .header("Authorization", "Bearer " + apiKey)
        .header("Content-Type", "application/json")
        ...
```

---

### 🟠 HIGH

**ChatServer.java line 69 — `executor.shutdown()` is non-blocking**

`stop()` calls `executor.shutdown()` and returns immediately. Running `ClientHandler` threads (e.g., mid Gemini call with 30s timeout) continue executing after the JVM shutdown hook completes. This risks incomplete message delivery.

**Fix:** Add `awaitTermination`:
```java
executor.shutdown();
try {
    if (!executor.awaitTermination(30, TimeUnit.SECONDS)) executor.shutdownNow();
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}
```

---

**GeminiService.java lines 83–146 — No rate limiting on AI requests**

Any connected client can send unlimited `AI_REQUEST` messages. Each triggers a Gemini API call costing quota and money. A single malicious client can drain quota for all users with no throttle.

**Fix:** Track last-request timestamp per username in `ClientHandler` and reject requests within a configurable window (e.g., 5 seconds).

---

**ChatServer.java lines 46–48 — Socket leaked on `RejectedExecutionException`**

```java
Socket socket = serverSocket.accept();
executor.submit(new ClientHandler(...));  // may throw if executor is shutting down
```

If `executor.submit()` throws (e.g., during shutdown), `socket` is never closed, leaking a file descriptor.

**Fix:**
```java
Socket socket = serverSocket.accept();
try {
    executor.submit(new ClientHandler(...));
} catch (RejectedExecutionException e) {
    try { socket.close(); } catch (IOException ignored) {}
}
```

### 🟡 MEDIUM

**ClientHandler.java lines 73–76 — Reader not closed on exception**

`BufferedReader reader` is created inside `run()` but there is no guarantee it is closed if an unhandled exception occurs during `handleLine()`. Holds native OS resources.

**Fix:** Use try-with-resources or explicitly close `reader` in a `finally` block.

---

**Message.java lines 115, 149 — `fileChunk` and `audioChunk` factories omit timestamp**

Every other factory method calls `m.timestamp = now()`. `fileChunk()` and `audioChunk()` do not. Chunks arrive at receivers with no timestamp, making it impossible to measure transfer time or order by arrival time.

**Fix:** Add `m.timestamp = now();` to both `fileChunk()` and `audioChunk()`.

---

**FileTransferManager.java line 64 / AudioTransferManager.java line 67 — Filename log injection**

File and audio names are echoed directly into log output without sanitization. A client sending a filename containing `\n` or `\r` can forge log lines.

**Fix:** Sanitize before logging:
```java
fileName.replace("\n", "\\n").replace("\r", "\\r")
```

---

**FileTransferManager.java line 48 / AudioTransferManager.java line 48 — `fileId` format unconstrained**

`fileId` is validated only for non-blank, not for format. If a client sends a crafted `fileId` containing special characters, it passes through to logs and relay messages.

**Fix:** Validate `fileId` is a valid UUID:
```java
try { UUID.fromString(fileId); }
catch (IllegalArgumentException e) { return "fileId must be a valid UUID."; }
```

---

**GeminiService.java line 117 — Backoff labeled "exponential" but is linear**

`Thread.sleep(RETRY_DELAY_MS * attempt)` produces 1.5s, 3s — linear growth, not exponential. Comments imply exponential backoff.

**Fix:** `Thread.sleep((long)(RETRY_DELAY_MS * Math.pow(2, attempt - 1)));`

---

**ClientManager.java lines 70–77 — Silent broadcast failure**

When `serializeQuietly()` fails (returns null), `broadcastExcept()` silently drops the entire message for all clients. No caller receives an indication that the broadcast failed.

**Fix:** Log at SEVERE level and (optionally) send a fallback ERROR message.

---

**GeminiService.java lines 34–38 — Model fallback chain hardcoded**

```java
private static final String[] MODEL_FALLBACK = {
    "gemini-2.0-flash", "gemini-1.5-flash", "gemini-1.5-pro",
};
```

When Google deprecates or renames models, a recompile is required.

**Fix:** Load from `application.properties` → `server.gemini.models=gemini-2.0-flash,gemini-1.5-flash,gemini-1.5-pro`.

---

### 🟢 LOW

**ChatServer.java line 41 — Default `ServerSocket` backlog (usually 50)**

Under high concurrent connects, the OS queue fills and new connections are dropped.

**Fix:** `new ServerSocket(config.getPort(), 256)`.

---

**Main.java lines 29–32 — No shutdown completion message**

Shutdown hook runs `chatServer.stop()` but logs nothing after. Operators cannot confirm the server finished shutting down.

**Fix:** Add `Logger.info("[JavaChat Server] Shutdown complete.");` after `chatServer.stop()`.

---

**application.properties — No logging configuration reference**

`Logger.java` attempts to load `logging.properties` at startup but this file is not documented in `application.properties`.

**Fix:** Add comment: `# See src/main/resources/logging.properties for log level/format config`.

## Desktop Client — Issues

### 🟡 MEDIUM

**MainFrame.java lines 155–159 — Audio buffer orphans never cleaned on `USER_LEFT`**

The `USER_LEFT` handler cleans up `fileBuffers` and `fileMeta` by sender, but the `removeIf` predicate for `audioBuffers` always returns `false`:

```java
audioBuffers.keySet().removeIf(fid -> {
    return false; // ← never removes anything
});
```

The comment says "audio orphans cleared below" but no code below clears them. If a sender departs mid-audio-transfer, their buffer stays in memory indefinitely.

**Fix:** Remove the dead `removeIf` block. Since `audioBuffers` keys do not store sender (server AUDIO_META relay doesn't carry sender in the buffer key), the simplest fix is to clear all `audioBuffers` entries whose corresponding `AUDIO_COMPLETE` was never received. The practical approach: remove the misleading no-op code and add a note documenting the known limitation.

Color[] palette = {

Minor code smell — the first palette color is the same hex as `ChatTheme.ACCENT` but defined inline.

**Fix:** Replace `new Color(0x00A884)` with `ChatTheme.ACCENT`.
